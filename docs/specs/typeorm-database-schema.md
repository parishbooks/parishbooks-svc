## 1. Entity List

All entities below except `Organization` extend `TenantEntity`
(`organizationId: uuid`, `createdAt`, `updatedAt`) from
`libs/shared/typeorm`. `Organization` itself is owned by the BetterAuth
TypeORM adapter — see `docs/architecture/multi-tenancy-betterauth.md` for
why it isn't a normal domain entity.

## 2. `@Index(['organizationId', 'id'])` Convention

Every `TenantEntity` subclass declares:

```ts
@Entity('member')
@Index(['organizationId', 'id'])
export class Member extends TenantEntity {
    /* ... */
}
```

This makes every tenant-scoped point lookup and paginated list query
(both of which always filter on `organizationId`) hit a single index
instead of a full-table scan filtered in memory. Additional targeted
composite indexes are added where a hot query needs them:

- `Donation`: `@Index(['organizationId', 'fundId'])` (fund-level reporting)
- `JournalLine`: `@Index(['organizationId', 'journalEntryId'])`
- `Account`: `@Unique(['organizationId', 'code'])`

## 3. Migration Workflow

```bash
npx typeorm migration:generate \
  -d libs/shared/typeorm/data-source.ts \
  libs/shared/typeorm/migrations/<Timestamp>-<Description>

npx typeorm migration:run -d libs/shared/typeorm/data-source.ts
```

- One `DataSource` config (`libs/shared/typeorm/data-source.ts`), shared by
  every service — there is one Postgres schema for the whole platform, not
  one per service.
- Generated migrations are **committed and reviewed like any other diff**:
  check for accidental column drops or type changes the ORM inferred
  incorrectly before merging.
- `synchronize: false` in every environment (CLAUDE.md rule 3). Local dev
  runs `migration:run` exactly like CI/prod does.
- `migration:run` in production is a gated CI/CD step, never run ad hoc
  against the prod database — see `docs/quality-ops/ci-cd-environments.md`.
- Naming: `<unix-timestamp>-<PascalCaseDescription>.ts`, one logical
  schema change per migration (don't bundle an unrelated column add into
  a migration named for a different feature).

## 4. Transaction / Unit-of-Work Pattern

Any write touching more than one entity runs inside a single TypeORM
`QueryRunner` transaction. The canonical example is posting a donation:

```ts
await this.dataSource.transaction(async (manager) => {
    const donation = await manager.save(Donation, { ...dto, organizationId });

    // LedgerService.postEntry is the ONLY sanctioned write path into
    // JournalEntry/JournalLine — see docs/specs/double-entry-ledger.md.
    const entry = await this.ledgerService.postEntry(manager, {
        organizationId,
        sourceType: 'donation',
        sourceId: donation.id,
        lines: [
            { accountId: cashAccountId, debit: donation.amount },
            { accountId: donation.accountId, credit: donation.amount },
        ],
    });

    donation.journalEntryId = entry.id;
    await manager.save(Donation, donation);
});
```

`postEntry` validates `SUM(debit) === SUM(credit)` for the given lines
_before_ issuing any insert, and throws (rolling back the whole
transaction, including the `Donation` row) if the entry doesn't balance.
No service outside `LedgerService` writes to `JournalEntry` or
`JournalLine` directly — this is what makes rule 2 in CLAUDE.md
enforceable in code review rather than just in prose.
